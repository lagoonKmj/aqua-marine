# 피부·두피 케어 샵용 웹 CRM — MVP 설계 (aqua-marine)

**문서 버전**: 1.0  
**작성일**: 2026-05-06  
**상태**: 브레인스토밍 승인 반영본

---

## 1. 목적·범위

### 1.1 목적

관리자 1명이 PC·모바일 브라우저에서 접속해 **고객 관리(CRM)** 를 중심으로, 전화 예약·당일 방문·시술·**휴대폰 촬영 사진 업로드**·결제·**선불(충전형) 적립**을 한 흐름으로 처리한다.

### 1.2 MVP 포함

- 반응형 웹, 관리자 인증 1계정 전제
- 고객 프로필(이름, 연락처, 생일, 메모), 검색·상세
- 예약: 날짜·시간·고객·메모·상태, 목록·필터(복잡한 슬롯 충돌 검사 없음)
- 방문 세션: “오늘 방문” 중심, 예약과 선택적 연결
- 시술 라인: 건별 청구 금액, **결제 수단 하나만**(지갑·현금·카드·이체 등)
- 선불 상품 카탈로그(예: 실수령 30만 원 → 지갑 적립 33만 원), 충전 시 원장 반영
- 시술 사진: **모바일 브라우저에서 촬영·업로드** (Storage + 메타데이터)
- 보안: RLS, 인증 사용자만 DB·스토리지 접근

### 1.3 MVP 제외(후속)

- 카카오 알림톡·SMS(생일 자동 발송 등) — 데이터만 적재, 연동은 후속
- 네이버 스마트플레이스 예약 동기화
- 미수금(외상), 할인·쿠폰(선불·지갑 중심으로 대체)
- 시술 건당 복수 결제 수단(섞어 결제)
- 세금계산서·현금영수증 등 외부 발행 연동
- 다점포·다계정(추가 관리자)

## 2. 아키텍처·스택

| 구분 | 선택 |
|------|------|
| 프론트·배포 | Next.js(App Router 권장), TypeScript, Vercel |
| 백엔드·데이터 | Supabase(PostgreSQL, Auth, Storage) |
| 비즈니스 규칙 | 지갑 차감·충전 등은 **PostgreSQL 트랜잭션 내 RPC(또는 Edge Function)** 로 일관성 유지; 구현 계획에서 단일 패턴 확정 |
| 테넌시 | 단일 매장, **단일 Auth 사용자** |

해외 리전·BaaS 사용을 허용하되, 실제 운영 시 **개인정보·민감정보(시술 사진) 처리방침·국외 이전·보관 기간** 은 사업자 준법 검토 대상이다.

## 3. 데이터 모델·도메인 규칙

### 3.1 엔티티(개념)

- **customers**: 고객 기본 정보, 생일(표시·필터용), 메모
- **prepaid_products**: `pay_amount`(실수령), `credit_amount`(지갑 적립), 활성 여부, 표시명
- **wallet_ledger**: `customer_id`, 유형(`topup` | `spend` | 선택적 `adjust`), 금액 필드(유형별 의미 명시), 관련 `prepaid_product_id` 또는 `treatment_line_id`, 타임스탬프
- **appointments**: 예정 일시, 고객, 메모, 상태(예정/취소/완료 등 단순 enum)
- **visits**: 방문 세션, 고객, 방문 시각, 상태, `appointment_id` nullable
- **treatment_lines**: `visit_id`, 시술 설명(또는 메뉴명), 청구 금액, **단일** `payment_method`, 지갑 결제 시 원장 `spend`와 동시 반영
- **treatment_photos**: Storage 객체 키, `treatment_line_id`(권장) 또는 `visit_id`, 업로드 시각

### 3.2 잔고

- **원장 합산**을 기준으로 하거나, `customers.wallet_balance` 캐시를 둘 경우 **RPC(또는 단일 트랜잭션 경로)에서만 갱신**하여 경쟁 상태를 줄인다.

### 3.3 규칙

1. **topup**: 등록된 선불 상품 선택 → 실제 입금 경로 기록(필드로 표현) → `credit_amount` 만큼 지갑 증가  
2. **spend**: 시술 라인이 지갑이면 잔액 검사 후 차감; 부족 시 전체 작업 실패  
3. 시술당 결제 수단은 **하나**  
4. 사진은 **모바일 촬영 업로드**를 주 사용 시나리오로 UI·용량·실패 메시지 설계

## 4. 주요 화면·업무 흐름

### 4.1 내비게이션(초안)

- **오늘**: 오늘 예약·오늘 방문·처리 대기 요약
- **고객**: 검색·목록·상세(잔고, 최근 방문·시술)
- **예약**: 등록·목록·날짜/상태 필터
- **방문/시술**: 방문 시작 → 시술 라인 추가(금액·수단) → 사진 업로드 → 완료
- **선불**: 고객 맥락에서 상품 선택 후 충전

### 4.2 권장 플로우

1. 전화 → 예약 저장 또는 당일 방문 시작  
2. **visit** 생성(예약 있으면 연결)  
3. 시술마다 **treatment_line** 추가 및 결제 수단 확정  
4. 동일 흐름에서 **휴대폰으로 촬영·업로드**  
5. 선불 판매 시 **카탈로그 상품만** 선택해 충전

---

## 5. 보안·에러 처리·품질

### 5.1 보안

- Supabase Auth, 최소 비밀번호 정책  
- PostgreSQL·Storage **RLS**: 익명 차단, 인증 사용자만 접근  
- HTTPS(Vercel)

### 5.2 에러·경계

- 지갑 부족: 사용자 메시지 + 수단 변경 유도  
- 업로드 실패: 재시도·원인 표시  
- 예약 노쇼·취소: 상태 필드로 단순 처리

### 5.3 테스트

- 도메인 단위 테스트: topup/spend, 잔액 부족, 단일 수단  
- 스테이징에서 RLS·Storage 스모크  
- 선택: 로그인→고객→충전→지갑 결제 E2E 한 경로

---

## 6. 비용·운영 전제

- 트래픽이 적을 때 Vercel·Supabase 무료(또는 저가) 티어로 시작 가능; 이미지 누적 시 Storage 비용 모니터링  
- 알림·외부 예약 연동은 과금·심사 요소가 있어 MVP에서 제외

---

## 7. 명시적 비결정(구현 계획에서 확정)

- `adjust`(수동 정정) 원장을 MVP에 포함할지 여부  
- 업로드 전 **클라이언트 리사이즈** 여부 및 최대 파일 크기  
- 시술 설명이 **자유 텍스트만** 인지, 간단 **메뉴 마스터** 테이블을 둘지 여부

---

## 8. 승인 이력(대화 기준)

- 아키텍처·스택(1안 BaaS), 데이터 모델·도메인, 화면·흐름, 보안·에러·테스트 섹션 사용자 승인 완료
